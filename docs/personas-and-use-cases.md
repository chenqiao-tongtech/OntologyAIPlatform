## 1. 文档目的

本文档定义本体工程平台的目标用户、用户职责、核心任务、典型使用场景和产品能力需求。

主要用于：

- 指导产品功能设计；
- 明确前端工作台和页面结构；
- 确定用户权限和角色模型；
- 为 MVP 需求拆分提供依据；
- 建立用户场景与系统模块之间的映射。

本文档中的角色是产品设计角色，不代表必须与企业实际组织架构中的岗位名称完全一致。

---

## 2. 用户角色总览

P1 面向五类主要用户。

| 角色 | 核心职责 | 使用平台的主要目的 |
|---|---|---|
| 企业数据架构师 | 企业数据模型和跨系统架构设计 | 建立统一业务语义 |
| 领域专家 | 业务概念和规则确认 | 审核本体定义 |
| 知识工程师 | 本体建模和语义质量管理 | 设计、编辑和验证本体 |
| AI 应用开发人员 | AI 应用和业务系统集成 | 获取并使用本体 |
| 平台管理员 | 平台配置、安全和资产管理 | 管理平台运行和权限 |

一个用户可以同时承担多个角色。

例如，小型团队中，数据架构师可能兼任知识工程师；在大型企业中，这些角色可能分别由不同部门承担。

## 3. 用户角色详细定义

### 3.1 企业数据架构师

**角色定位**

负责企业数据架构、跨系统数据模型和业务语义的一致性。

**主要关注**

- 不同业务系统的数据模型；
- 核心业务对象；
- 数据字段与业务概念的对应关系；
- 跨系统数据映射；
- 语义资产的复用和影响范围。

**典型任务**

1. 创建企业级本体项目；
2. 连接 CRM、ERP、OMS 等数据源；
3. 查看数据库结构和元数据；
4. 识别不同系统中的同义或相似字段；
5. 设计统一业务概念；
6. 审核跨系统数据映射；
7. 查看本体版本差异；
8. 发布企业级领域本体。

**主要痛点**

- 不同系统模型缺少统一定义；
- 依赖人工整理数据字典；
- 业务系统变化难以同步到语义模型；
- 缺少统一模型复用机制。

**平台能力需求**

- 项目和领域管理；
- 数据源连接器；
- 元数据浏览；
- 术语管理；
- 本体设计器；
- 映射关系管理；
- 版本差异和发布。

**成功标准**

能够建立跨系统业务对象模型，并追溯模型元素与原始数据资产之间的关联。

### 3.2 领域专家

**角色定位**

负责业务概念、业务关系和业务规则的准确性确认。

**主要关注**

- 业务术语是否准确；
- 概念边界是否合理；
- 实体关系是否符合业务实际；
- 属性定义是否正确；
- AI 生成建议是否存在错误。

**典型任务**

1. 查看 AI 生成的候选本体；
2. 查看候选概念的业务定义；
3. 阅读关联的文档和数据来源；
4. 确认实体和关系；
5. 修改错误定义；
6. 拒绝不合理的候选；
7. 对存在歧义的概念提出补充说明；
8. 确认正式业务定义。

**主要痛点**

- 技术建模工具不够直观；
- 业务定义分散在文档中；
- 不容易理解 OWL、RDF 等技术表达；
- 难以判断 AI 建议的依据。

**平台能力需求**

- 术语和概念浏览；
- 可视化本体结构；
- 证据查看；
- 候选审核；
- 差异比较；
- 简单易用的编辑界面。

**成功标准**

领域专家能够在不直接编写 RDF/OWL 代码的情况下，完成关键业务语义的确认和审核。

### 3.3 知识工程师

**角色定位**

负责本体的专业设计、结构维护和语义质量。

**主要关注**

- 元模型设计；
- Class 和 Property；
- Object Property 和 Data Property；
- 继承和关系结构；
- OWL/RDF 表达；
- SHACL 约束；
- 本体一致性和互操作性。

**典型任务**

1. 创建和编辑本体；
2. 定义类、属性和关系；
3. 设置域和值域；
4. 管理继承关系；
5. 编写约束；
6. 检查本体结构；
7. 执行 SHACL 验证；
8. 导入和导出标准本体；
9. 管理版本和变更；
10. 处理审核过程中发现的语义问题。

**主要痛点**

- 企业本体维护工具不足；
- 多来源候选模型难以合并；
- 标准兼容性和格式转换存在成本；
- 本体版本管理不完善；
- 需要同时处理业务和技术问题。

**平台能力需求**

- 专业本体编辑器；
- 元模型管理；
- RDF/OWL 导入导出；
- SHACL 验证；
- 语义规则管理；
- 版本和差异比较；
- 证据和变更追溯。

**成功标准**

能够设计、维护和发布符合项目标准的本体，并通过平台验证机制发现模型问题。

### 3.4 AI 应用开发人员

**角色定位**

负责将企业语义资产集成到 RAG、Agent、数据分析和业务应用中。

**主要关注**

- 如何查询本体；
- 如何理解业务对象；
- 如何获取属性和关系；
- 如何将自然语言映射到业务语义；
- 如何管理应用使用的本体版本。

**典型任务**

1. 查询已发布的本体；
2. 获取实体、属性和关系定义；
3. 查询术语和别名；
4. 获取业务概念的来源说明；
5. 下载或导出本体；
6. 将本体接入 Agent 或 RAG；
7. 在应用中记录所使用的本体版本；
8. 根据新版本调整应用。

**主要痛点**

- 不同 AI 应用重复理解业务概念；
- 业务定义缺少统一接口；
- 语义模型变化后难以获知；
- 缺少稳定的版本引用。

**平台能力需求**

- 本体查询 API；
- 标准导出；
- 术语查询接口；
- 版本标识；
- 语义资产引用；
- 开发文档和 SDK（按阶段建设）。

**成功标准**

能够通过稳定接口获取指定版本的本体，并在 AI 应用中复用。

### 3.5 平台管理员

**角色定位**

负责平台自身的用户、权限、配置和运行管理。

**主要关注**

- 用户和组织；
- 项目权限；
- 数据源凭据；
- 连接器运行；
- 任务状态；
- 操作审计；
- 存储和备份；
- 平台部署和升级。

**典型任务**

1. 创建用户和组织；
2. 分配角色和权限；
3. 配置数据源连接；
4. 管理密钥和凭据引用；
5. 查看发现任务和验证任务状态；
6. 查看系统错误；
7. 查看操作审计；
8. 备份和恢复平台数据；
9. 执行升级和配置管理。

**主要痛点**

- 数据源凭据管理复杂；
- 不同用户访问边界不明确；
- 后台任务运行状态难以追踪；
- 平台部署和升级缺少统一文档。

**平台能力需求**

- 用户和角色管理；
- RBAC 权限控制；
- 数据源连接管理；
- 任务管理；
- 审计日志；
- 健康检查；
- 部署和备份文档。

**成功标准**

能够安全地管理平台资源、用户权限和数据源连接，并追踪关键操作。

## 4. 典型用户协作关系

一个企业本体项目通常不是由单一角色独立完成。

典型协作关系如下：

```text
              企业数据架构师
                     │
              创建项目和领域
                     │
                     ▼
               本体工程平台
                     │
          连接数据源、采集元数据
                     │
                     ▼
              AI 本体发现服务
                     │
                生成候选模型
                     │
                     ▼
                知识工程师
                     │
               检查和编辑模型
                     │
                     ▼
                 领域专家
                     │
               确认业务语义
                     │
                     ▼
                语义验证
                     │
                     ▼
                版本和发布
                     │
                     ▼
              AI 应用开发人员
                     │
               集成和复用本体

       平台管理员负责权限、配置和审计
```

该流程描述的是典型业务协作方式，具体审批步骤和权限配置可根据组织规模调整。

## 5. 核心使用场景

### UC-01：创建本体工程项目

**目标用户：** 企业数据架构师、知识工程师。

**业务目标：** 创建一个用于管理特定业务领域本体的项目。

**前置条件：**

- 用户已登录；
- 用户具有项目创建权限。

**基本流程：**

1. 用户进入项目管理页面；
2. 创建新项目；
3. 输入项目名称、描述和所属领域；
4. 选择本体项目配置；
5. 设置项目成员；
6. 保存项目；
7. 平台生成项目唯一标识。

**异常流程：**

- 项目名称重复；
- 用户无创建权限；
- 必填信息缺失；
- 保存失败。

**系统产出：**

- Ontology Project；
- 项目元数据；
- 项目成员和权限配置。

**验收标准：**

能够创建项目、查询项目详情，并保证项目数据具有稳定标识。

### UC-02：连接企业数据源

**目标用户：** 企业数据架构师、平台管理员。

**业务目标：** 将企业现有 IT 资产接入本体工程平台。

**前置条件：**

- 项目已创建；
- 用户具有数据源管理权限；
- 外部数据源允许访问。

**基本流程：**

1. 用户选择数据源类型；
2. 填写连接配置；
3. 配置安全凭据引用；
4. 平台测试连接；
5. 用户确认连接；
6. 平台保存数据源配置；
7. 用户启动元数据采集。

**首期数据源类型建议：**

- PostgreSQL；
- MySQL；
- 常见文档文件；
- OpenAPI/JSON Schema；
- Git 仓库。

具体支持范围以连接器实现和测试结果为准。

**异常流程：**

- 网络连接失败；
- 认证失败；
- 权限不足；
- 数据源类型不支持；
- 采集任务失败。

**系统产出：**

- Data Source；
- Connection Configuration；
- Metadata Collection Job。

**安全要求：**

- 默认只读；
- 不在日志中暴露密码和令牌；
- 凭据通过安全引用管理；
- 对外部网络访问实施限制。

**验收标准：**

能够安全连接测试数据源，并记录连接状态和采集任务结果。

### UC-03：采集和浏览元数据

**目标用户：** 企业数据架构师、知识工程师。

**业务目标：** 将外部 IT 资产的结构信息转化为平台统一管理的元数据资产。

**基本流程：**

1. 选择已配置的数据源；
2. 启动元数据采集；
3. 平台识别表、字段、类型和约束；
4. 将采集结果映射为 Metadata Asset；
5. 用户查看元数据；
6. 用户选择需要进一步发现的资产。

**数据库元数据至少包括：**

- Schema；
- Table；
- Column；
- Data Type；
- Primary Key；
- Foreign Key；
- Index；
- Comment。

**系统产出：**

- Metadata Asset；
- Source Reference；
- Collection Evidence。

**验收标准：**

能够正确采集测试数据库中的指定结构信息，并能够追溯来源。

### UC-04：AI 自动发现本体候选

**目标用户：** 知识工程师、企业数据架构师。

**业务目标：** 从企业现有资产中生成候选业务概念和关系。

**前置条件：**

- 项目已经创建；
- 数据源元数据已采集；
- 已配置可用的 AI Discovery Provider；
- 用户具有发现任务执行权限。

**基本流程：**

1. 用户选择需要分析的数据资产；
2. 创建发现任务；
3. 选择发现范围和任务参数；
4. 平台调用 Discovery Provider；
5. AI 分析字段、注释和文档；
6. 生成实体、属性、关系和术语候选；
7. 平台保存候选结果；
8. 为候选结果关联来源证据；
9. 用户查看发现报告。

**候选内容示例：**

- Customer；
- Order；
- Product；
- Customer places Order；
- Order contains Product。

**系统产出：**

- Discovery Job；
- Discovery Proposal；
- Evidence；
- Discovery Report。

**异常流程：**

- Provider 不可用；
- 输入数据不完整；
- 模型输出格式错误；
- 任务超时；
- 发现结果缺少必要证据。

**验收标准：**

能够从固定测试数据生成结构化候选，并保存任务配置、结果和来源信息。

不得将候选生成结果直接视为正式本体。

### UC-05：审核和编辑 AI 候选

**目标用户：** 领域专家、知识工程师。

**业务目标：** 将 AI 生成的候选模型转化为经过确认的本体定义。

**基本流程：**

1. 用户进入候选审核页面；
2. 查看候选实体和关系；
3. 查看来源证据；
4. 比较候选定义和现有本体；
5. 接受、修改或拒绝候选；
6. 处理重复概念和冲突关系；
7. 保存审核结果；
8. 将通过审核的候选合并到工作版本。

**建议的候选状态：**

- Pending；
- In Review；
- Accepted；
- Modified；
- Rejected；
- Merged；
- Needs Evidence。

**系统产出：**

- Review Record；
- Updated Ontology Model；
- Change Record。

**验收标准：**

每个候选都能够记录审核状态、操作人员、操作时间和最终处理结果。

### UC-06：创建和编辑本体

**目标用户：** 知识工程师、领域专家。

**业务目标：** 创建和维护正式的领域本体。

**基本流程：**

1. 用户进入本体设计器；
2. 查看类和属性结构；
3. 创建或修改 Class；
4. 创建或修改 Property；
5. 设置对象关系；
6. 配置继承和约束；
7. 保存工作版本；
8. 查看修改结果。

**核心操作：**

- 新建 Class；
- 编辑 Class；
- 删除或停用元素；
- 新建 Data Property；
- 新建 Object Property；
- 设置 Domain 和 Range；
- 管理继承关系；
- 管理术语和别名；
- 编辑约束；
- 查看模型结构图。

**验收标准：**

编辑操作能够正确持久化，并通过模型读取接口重新加载；关键修改能够形成变更记录。

### UC-07：执行语义验证

**目标用户：** 知识工程师。

**业务目标：** 在本体保存或发布前发现结构和语义问题。

**基本流程：**

1. 用户选择本体版本；
2. 选择验证规则集；
3. 启动验证；
4. 平台执行结构和语义检查；
5. 生成验证报告；
6. 用户查看错误和警告；
7. 修复问题；
8. 重新执行验证。

**建议检查内容：**

- JSON Schema；
- 稳定 ID 和唯一性；
- 元素引用完整性；
- 类和属性定义；
- Domain 和 Range；
- RDF/OWL 语法；
- SHACL 约束；
- 项目间引用边界；
- 自定义业务规则。

**系统产出：**

- Validation Run；
- Validation Finding；
- Validation Report。

**验收标准：**

能够通过正向和反向测试用例验证规则有效性，并将错误定位到具体本体元素。

### UC-08：管理本体版本和发布

**目标用户：** 知识工程师、企业数据架构师。

**业务目标：** 将经过审核和验证的本体发布为正式语义资产。

**基本流程：**

1. 用户选择工作版本；
2. 平台生成版本差异；
3. 执行发布前验证；
4. 用户确认审核结果；
5. 创建不可变发布快照；
6. 生成发布版本标识；
7. 保存发布记录；
8. 提供本体查询和导出接口。

**建议版本信息：**

- Version ID；
- Version Number；
- Created By；
- Created At；
- Parent Version；
- Validation Result；
- Review Record；
- Release Status。

**验收标准：**

发布版本能够稳定读取；历史版本内容不因后续编辑而发生变化；发布记录可以追溯对应验证和审核结果。

### UC-09：查询和复用已发布本体

**目标用户：** AI 应用开发人员。

**业务目标：** 将平台中的本体资产接入其他应用。

**基本流程：**

1. 开发人员查询已发布本体；
2. 选择本体和版本；
3. 获取本体结构；
4. 获取术语和关系定义；
5. 下载标准格式文件或调用 API；
6. 在应用中引用该版本；
7. 根据后续版本变化评估升级。

**建议提供的接口：**

- 本体项目查询；
- 本体详情查询；
- 类和属性查询；
- 术语查询；
- 关系查询；
- 版本查询；
- RDF/OWL 导出；
- 发布状态查询。

**验收标准：**

能够通过稳定 API 获取指定版本内容，且返回数据与发布快照一致。

### UC-10：本体结构和知识图谱可视化

**目标用户：** 知识工程师、领域专家、AI 应用开发人员。

**业务目标：** 通过图形界面理解本体结构及其在实例数据中的应用。

**基本流程：**

1. 用户选择本体或知识图谱；
2. 平台识别当前查看对象类型；
3. 显示类、属性和关系，或实例实体及其关系；
4. 用户缩放、筛选和展开节点；
5. 用户查看节点详情；
6. 用户定位对应本体定义和来源。

**必须区分的两类视图：**

**Ontology Schema View**

展示类、属性、继承关系、对象关系和约束。

**Knowledge Graph Instance View**

展示具体实例、实例属性和实例关系。

两种视图应具有不同的数据接口和交互逻辑。

**验收标准：**

能够正确展示测试模型中的节点和关系，并支持基本查询、筛选和详情查看。

大规模图谱的性能指标需要在确定数据规模和部署环境后另行定义。

### UC-11：平台管理与审计

**目标用户：** 平台管理员。

**业务目标：** 安全管理平台资源和关键操作。

**基本流程：**

1. 管理员创建用户；
2. 分配角色和项目权限；
3. 配置数据源；
4. 查看后台任务；
5. 查看失败记录；
6. 查看审计事件；
7. 管理平台配置和运行状态。

**关键审计事件：**

- 用户登录；
- 项目创建；
- 数据源配置变更；
- 发现任务启动；
- 本体修改；
- 审核决策；
- 验证执行；
- 版本创建；
- 本体发布；
- 权限变更。

**验收标准：**

关键操作能够记录操作者、时间、对象、操作类型和结果；权限检查能够阻止未授权访问。

## 8. 首期 MVP 的用户场景优先级

## 10. 产品设计注意事项

### 10.1 领域专家界面应避免过度技术化

领域专家主要关心业务含义和来源依据。

不应要求其直接理解 RDF 三元组、OWL 公理或 SPARQL。

### 10.2 知识工程师需要专业能力

专业用户需要查看底层语义结构、标准映射和约束定义。

因此，平台应兼顾易用界面和专业编辑能力。

### 10.3 AI 候选必须与正式资产区分

候选模型不能自动进入正式发布版本。

需要清晰展示候选状态、来源证据和审核结果。

### 10.4 可视化不能替代数据管理

图形编辑和关系展示只是交互方式。

最终数据必须持久化到统一的领域模型和版本管理体系中。

### 10.5 权限和审计应贯穿核心操作

不能只在管理后台实现权限控制。

项目访问、数据源配置、模型编辑、审核和发布都需要执行相应权限检查。
