## 1. 产品概述

### 1.1 产品背景

随着企业数字化建设持续推进，企业内部已经积累了大量结构化和非结构化信息，包括关系型数据库、数据仓库、业务系统、API、技术文档、代码仓库以及知识图谱等。

这些资产承载着企业的业务数据和业务知识，但不同系统通常采用各自的数据模型、字段命名和业务定义。

同一个业务对象可能在不同系统中拥有不同名称、属性和状态定义；同一个业务术语也可能在不同部门中具有不同含义。

传统的数据集成、数据目录和知识图谱技术能够解决其中一部分问题，但企业仍然缺少一套能够持续管理业务语义定义的工程体系。

大语言模型进一步降低了业务知识发现和语义建模的门槛，使自动识别业务概念、生成关系建议和辅助本体构建成为可能。

但 AI 生成的语义模型仍然需要审核、验证、版本管理和来源追溯。

因此，我们需要建设一套面向企业语义资产的工程化管理平台。

### 1.2 产品定义

Ontology Engineering Platform 是一套面向企业语义资产的工程化管理平台。

平台通过连接企业现有数据和 IT 资产，利用 AI 辅助发现业务概念、实体、属性、关系和约束，并提供本体创建、编辑、审核、验证、版本管理、发布和可视化能力。

平台的目标是帮助企业建立一套可持续维护、可追溯、可验证、可复用的语义资产体系，为 AI 应用、知识图谱、数据分析和业务系统提供统一的语义基础。

### 1.3 核心定位

**将企业分散的业务语义转化为可发现、可建模、可验证、可管理和可复用的工程资产。**

平台的核心对象不是单一的 OWL 文件，也不是单一知识图谱，而是围绕本体及其关联资产形成的完整工程生命周期。

## 2. 产品愿景

### 2.1 长期愿景

建设面向企业 AI 时代的语义资产工程基础设施。

企业可以通过平台：

1. 自动发现现有 IT 资产中的业务语义；
2. 建立统一的领域本体和业务概念体系；
3. 通过 AI 与人工协作持续完善语义模型；
4. 对本体进行标准化验证和版本管理；
5. 将本体发布为可供不同系统使用的语义资产；
6. 根据业务系统和数据资产的变化持续维护本体。

最终使企业语义模型从一次性知识工程项目，转变为能够持续演进的工程资产。

### 2.2 产品使命

降低企业本体建设和维护的技术门槛，提升语义资产的质量、可维护性和复用能力。

### 2.3 产品价值主张

| 价值方向 | 解决的问题 | 产品提供的价值 |
|---|---|---|
| 语义统一 | 不同系统的业务定义不一致 | 建立统一领域概念和关系模型 |
| 自动发现 | 本体建设依赖人工阅读大量资料 | 利用 AI 辅助发现候选语义模型 |
| 工程管理 | 本体通常以文件或项目形式管理 | 提供完整生命周期管理 |
| 质量保障 | 模型错误和语义冲突难以发现 | 提供结构与语义验证 |
| 资产复用 | 不同团队重复建设相似模型 | 提供统一的本体资产和发布接口 |
| 变更追溯 | 业务变化后难以识别模型影响 | 提供版本、差异和来源追溯 |

## 3. 目标用户与服务对象

平台主要服务于以下角色：

| 用户角色 | 主要需求 |
|---|---|
| 企业数据架构师 | 统一跨系统数据模型和业务语义 |
| 领域专家 | 定义和审核业务概念、关系与规则 |
| 知识工程师 | 设计、维护和验证本体 |
| AI 应用开发团队 | 获取统一语义模型并集成到 AI 应用 |
| 企业架构师 | 管理企业级语义资产和系统间关系 |
| 平台管理员 | 管理项目、用户、权限、连接器和运行配置 |

平台既要支持专业知识工程人员，也要让不熟悉 OWL/RDF 的业务专家能够参与本体审核和维护。

## 4. 产品设计原则

### 4.1 标准兼容

采用开放的语义表示和交换标准，重点考虑：

- RDF：资源描述框架；
- RDFS：RDF Schema；
- OWL：Web Ontology Language；
- SHACL：RDF 图约束验证；
- JSON Schema：结构化数据验证；
- SKOS：术语和分类体系管理。

平台内部可以采用适合工程实现的统一元模型，但必须提供清晰的标准映射和导入导出机制。

不要求首期完整实现所有标准规范，而是明确支持范围、兼容性边界和不支持的语法。

### 4.2 AI 辅助、人类负责

AI 负责理解资料、发现候选概念、提出关系建议和辅助建模。

正式语义定义需要经过必要的审核和验证。

AI 生成结果默认视为候选资产，不应自动成为正式发布版本。

### 4.3 证据可追溯

重要的本体元素应尽可能关联其来源信息。

来源可以包括：

- 数据库表和字段；
- 文档及其章节；
- API 定义；
- 代码文件和符号；
- 人工输入和审核记录；
- AI 发现任务及模型版本。

平台应能够回答：某个概念为什么这样定义？依据来自哪里？由谁确认？在哪个版本中生效？

### 4.4 生命周期管理

本体应具有明确的创建、编辑、审核、验证、版本和发布过程。

正式发布版本应具有稳定标识，并能够追溯对应的模型内容、审核记录和验证结果。

### 4.5 模块化与可扩展

连接器、AI 发现引擎、标准解析器和可视化组件应具有明确的扩展接口。

外部工具应通过适配层接入，避免平台核心逻辑绑定单一供应商或模型。

### 4.6 安全优先

- 数据源连接默认只读；
- 敏感凭据采用安全引用方式管理；
- 访问权限遵循最小权限原则；
- 外部文件解析应进行隔离；
- AI 输出和外部输入均视为不可信数据；
- 关键操作保留审计记录；
- 不允许本体发现任务直接获得生产业务操作权限。

## 5. P1 产品范围

P1 聚焦本体工程生命周期，规划八类核心能力。

| 模块 | 核心功能 | 主要产出 |
|---|---|---|
| 本体项目管理 | 项目、领域和本体管理 | 本体工程项目 |
| 元模型管理 | 管理本体元素和元模型定义 | 统一语义模型结构 |
| 数据源连接 | 连接数据库、文档、API 和代码仓库 | 数据源与元数据资产 |
| AI 本体发现 | 自动识别概念、属性、关系和约束候选 | 本体发现建议 |
| 本体设计与审核 | 可视化编辑、差异比较、人工审核 | 经审核的本体模型 |
| 语义验证 | 结构、引用、标准和语义约束验证 | 验证报告和问题清单 |
| 版本与发布 | 变更管理、版本比较和正式发布 | 可追溯本体版本 |
| 可视化探索 | 本体结构和知识图谱展示 | 语义模型可视化 |

### 5.1 首期 MVP 的核心闭环

P1 首期不以模块数量作为验收标准，而以一条完整、可重复的本体工程链路作为核心目标：

```text
创建本体项目
    ↓
连接数据源
    ↓
采集元数据
    ↓
AI 生成候选本体
    ↓
关联来源证据
    ↓
人工审核和编辑
    ↓
执行语义验证
    ↓
保存版本
    ↓
发布本体
    ↓
通过接口查询和复用
```

首期优先完成这一闭环所必需的功能。

### 5.2 标准支持策略

首期建议采用以下分层策略：

- 内部元模型：作为统一业务对象和工程管理模型；
- JSON Schema：用于内部对象结构验证和 API 契约；
- RDF/RDFS/OWL：用于本体表达和标准互操作；
- SHACL：用于 RDF 图结构和约束验证；
- SKOS：在术语管理场景中按需支持。

对复杂 OWL 公理、推理和其他高级语义能力，应通过明确的兼容性矩阵逐步扩展。

## 6. 产品边界

P1 不承担以下职责：

| 非目标 | 说明 |
|---|---|
| 企业数据库 | 不承担核心业务数据存储和事务处理 |
| 完整数据治理平台 | 不替代主数据、数据质量和数据治理体系 |
| 通用知识图谱数据库 | 不要求首期提供完整图数据库能力 |
| Agent Runtime | 不负责多智能体的运行、调度和监控 |
| 生产业务授权 | 不负责生产环境的业务操作审批和执行授权 |
| 通用工作流引擎 | 不建设复杂跨部门企业流程平台 |
| 行业业务应用 | 不在通用平台 MVP 中直接建设完整行业应用 |

P1 可以与这些系统集成，但不以替代它们为产品目标。

## 7. 产品架构方向

### 7.1 总体架构

产品初期建议采用模块化单体架构，并通过异步 Worker 处理数据采集、AI 发现和批量验证等任务。

主要分层：

1. **交互层**：项目工作台、本体编辑器、审核界面、可视化探索器。
2. **应用服务层**：项目管理、数据源管理、发现任务、验证、版本和发布服务。
3. **语义核心层**：统一元模型、标准转换、语义验证和模型管理。
4. **任务执行层**：连接器执行、文件解析、AI Provider 和后台任务。
5. **基础设施层**：数据库、对象存储、消息队列、身份认证和日志审计。

### 7.2 技术路线参考

| 技术领域 | 建议技术 | 选择理由 |
|---|---|---|
| 前端 | React / Next.js / TypeScript | 适合复杂管理界面和图形交互 |
| 后端 | Python / FastAPI | 便于集成 AI 和语义处理库 |
| 主数据库 | PostgreSQL | 管理项目、模型、版本和元数据 |
| 对象存储 | MinIO / S3 | 保存文件、导入导出物和证据 |
| 异步任务 | Celery / Redis | 处理长时间运行的发现与验证任务 |
| RDF 处理 | RDFLib | RDF 数据解析和转换 |
| SHACL 验证 | pySHACL | RDF 图约束验证 |
| JSON 验证 | JSON Schema | 内部结构和 API 契约验证 |
| 图形展示 | Cytoscape.js | 本体和关系图可视化 |
| 身份认证 | OIDC / Keycloak（按需） | 支持企业身份体系 |

上述为技术路线建议，最终以技术验证和架构决策记录为准。

### 7.3 外部工具集成原则

外部工具采用 Provider / Adapter 方式集成。

例如，AI 本体发现工具可以接入统一的 Discovery Provider 接口。

平台负责项目、模型、审核、证据、版本和发布等核心资产管理；外部工具负责特定的发现、解析或推理任务。

外部工具不应直接成为平台唯一的数据模型或系统记录来源。

## 9. 产品成功标准

P1 的成功不能仅通过功能数量、代码规模或模型生成数量衡量。

重点关注：

1. 是否能够从真实或可重复的测试数据源采集元数据；
2. 是否能够生成带有来源证据的本体候选；
3. 是否能够通过人工审核修改候选模型；
4. 是否能够发现结构和语义问题；
5. 是否能够保存可追溯版本；
6. 是否能够发布并通过接口复用；
7. 是否能够在干净环境中部署和运行；
8. 是否具有可重复的测试和验收记录。

### 核心验收原则

**至少完成一条从数据源到正式发布本体的完整工程闭环，并能够在测试环境中重复验证。**

## 10. 与未来产品体系的关系

P1 是未来 ODAP 产品体系中的本体工程基础模块，不代表整个 ODAP 产品家族。

规划中的产品方向：

| 产品 | 定位 | 与 P1 的关系 |
|---|---|---|
| P1 Ontology Engineering Platform | 本体发现、建模、验证和管理 | 当前建设对象 |
| P2 Agent Control Plane | Agent 管理、运行控制和监控 | 使用 P1 提供的语义资产 |
| P3 Semantic Gateway & Data Connectivity | 语义访问和数据连接 | 与 P1 的连接器和语义接口协同 |
| P4 Evidence & Evaluation Platform | 证据、评估和质量体系 | 可消费 P1 的证据和验证记录 |
| P5 Workflow & Action Governance | 工作流和业务动作治理 | 可引用 P1 的语义定义和约束 |

上述为产品规划方向，不代表各产品已经实现或完成技术验证。

- 产品目标或主要用户发生变化；
