# ADR-0001: 首期采用模块化单体与异步 Worker

- Status: Accepted for MVP design
- Date: 2026-11-21
- Decision Owners: P1 Architecture
- Scope: P1 Backend Architecture

## 1. Context

P1 包含项目管理、本体建模、连接器、元数据采集、AI 发现、审核、验证、版本和发布等多个模块。

不同模块具有独立的业务职责，但首期产品仍处于核心功能验证和工程闭环建设阶段。

如果从一开始采用微服务，将额外引入服务发现、分布式部署、跨服务调用、分布式事务、日志追踪和服务治理等复杂度。

同时，数据采集、AI 推理、文件解析和复杂验证又存在明显的长耗时执行需求。

## 2. Decision

采用：

**模块化单体 + 异步 Worker + 消息 Broker。**

后端使用一个 FastAPI 应用承载核心业务模块。各模块通过应用服务接口协作，禁止直接访问其他模块的内部实现。

独立 Worker 负责长时间运行的任务。

## 3. Alternatives

### A. 全量微服务

优点：
- 模块可独立部署和扩缩容；
- 技术栈选择更加灵活；
- 服务故障可以进行更细粒度隔离。

缺点：
- 部署、测试和运维成本增加；
- 服务间调用及数据一致性更加复杂；
- 首期团队需要承担更多基础设施开发。

### B. 普通单体

优点：
- 简单易部署；
- 开发和调试成本低。

缺点：
- 模块边界容易模糊；
- 业务逻辑和数据访问容易产生耦合；
- 后续拆分成本高。

### C. 模块化单体 + 异步 Worker

优点：
- 保留清晰的代码边界；
- 部署单元数量可控；
- 长耗时任务可以独立运行；
- 后续能够按模块拆分服务。

缺点：
- 模块边界需要通过代码规范和测试持续维护；
- 同一个业务应用的发布仍然具有一定整体性。

## 4. Consequences

### Positive
- MVP 部署复杂度可控；
- 可以优先实现完整的本体生命周期；
- 后台任务可以独立扩容；
- 具备后续服务拆分条件。

### Negative
- 不能为每个业务模块独立选择运行时和发布周期；
- 模块间边界需要持续治理；
- 单个 API 进程的资源使用需要监控。

## 5. Implementation Constraints

- 每个模块定义独立职责和服务接口。
- 不允许跨模块直接访问内部 Repository。
- 长时间运行的任务必须提交到异步队列。
- Worker 必须具备超时、重试和幂等机制。
- 数据访问必须执行项目和租户范围检查。
- 异步任务结果必须关联 Job ID 和来源记录。

## 6. Service Extraction Criteria

满足以下条件之一时，可以提出独立服务拆分：

- 某模块需要独立扩容；
- 某模块需要不同的运行时环境；
- 某模块对故障隔离具有明确要求；
- 模块拥有稳定的接口和数据边界；
- 已经具备独立开发、部署和维护能力。

## 7. Validation

- [ ] 单个模块可以通过服务接口独立测试。
- [ ] 长耗时任务不会阻塞 API 请求。
- [ ] Worker 重试不会产生重复的正式资产。
- [ ] 模块之间不存在未经授权的数据访问。
- [ ] 核心模块能够通过接口边界进行独立替换。

## 8. Status

Accepted for the MVP architecture design. Service extraction remains a future decision and requires a separate ADR.
