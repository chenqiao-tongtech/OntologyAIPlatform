## 1. 文档目的

本文档用于定义本体工程平台需要解决的核心问题，描述企业语义资产管理中的典型困难、业务影响、目标问题和产品需求来源。

本文档是产品需求、架构设计和 MVP 范围确定的输入依据。

本文件不预设所有企业都存在相同问题，也不将未经验证的市场判断当作事实。具体客户场景需要在后续访谈和产品验证中进一步确认。

## 2. 核心问题陈述

### 2.1 问题定义

企业的业务语义分散在数据库、业务系统、文档、API、代码和知识图谱中。

不同系统和团队对同一业务对象可能采用不同的名称、属性、状态和规则，缺乏统一、可追溯的语义关联机制。

传统本体建模工具主要关注模型表达和编辑，而企业实际需要持续开展语义发现、审核、验证、版本管理和发布。

大模型能够辅助理解和生成语义模型，但无法天然保证生成结果准确、稳定和可追溯。

因此，企业需要一套能够将分散语义转化为可持续管理的工程资产的平台。

### 2.2 问题核心

可以归纳为五个方面：

1. 语义定义分散；
2. 语义关联缺失；
3. 本体建设依赖人工；
4. 本体质量和变更缺少工程管理；
5. 语义资产难以跨应用复用。

## 3. 企业语义管理的典型问题

### 3.1 问题一：同一业务概念在不同系统中定义不一致

**典型场景**

CRM、OMS 和 ERP 都记录客户信息，但字段名称、属性定义和业务边界不同。

例如：

| 系统 | 字段 | 可能的业务含义 |
|---|---|---|
| CRM | customer_id | CRM 客户记录标识 |
| OMS | buyer_code | 下单购买方标识 |
| ERP | cust_no | 财务客户账户标识 |

这些字段不一定代表完全相同的实体。

如果仅凭名称或字段类型进行映射，可能造成错误的数据关联。

**根本原因**

- 各系统独立设计；
- 缺少统一领域概念定义；
- 业务语义没有与字段建立稳定映射；
- 系统演进时缺少跨系统同步机制。

**业务影响**

- 数据整合需要重复编写映射规则；
- 跨系统分析口径不一致；
- AI 应用难以正确理解业务对象；
- 系统改造需要依赖熟悉历史设计的人员。

**P1 应对方向**

- 建立统一领域本体；
- 识别跨系统同义和近义概念；
- 保存本体元素与数据字段的映射；
- 记录映射依据和审核状态。

### 3.2 问题二：同一术语在不同业务上下文中含义不同

**典型场景**

“订单金额”在不同业务环节可能指：

- 商品原始金额；
- 优惠后金额；
- 应付金额；
- 已支付金额；
- 含税金额；
- 已结算金额。

如果不区分上下文，AI 应用可能使用错误的金额字段回答业务问题。

**根本原因**

- 缺少术语定义；
- 缺少业务上下文；
- 指标口径分散；
- 业务规则未形成可复用的语义表达。

**业务影响**

- 数据分析结果不一致；
- 跨部门沟通成本增加；
- AI 回答存在语义歧义；
- 业务规则重复实现。

**P1 应对方向**

- 建立术语和别名管理；
- 为概念定义业务上下文；
- 将属性与业务定义关联；
- 对存在冲突的定义保留独立概念或上下文。

### 3.3 问题三：业务语义分散在多种 IT 资产中

**典型场景**

一个订单状态的定义可能同时存在于：

- 数据库枚举字段；
- API 响应结构；
- Java/Python 代码枚举；
- 业务流程文档；
- 测试用例；
- 操作手册。

这些定义未必同步更新。

**根本原因**

- 缺少跨资产语义关联；
- 文档和代码分别维护；
- 元数据采集和更新机制不统一；
- 语义模型与原始资产之间缺少引用关系。

**业务影响**

- 难以判断定义的真实来源；
- 业务变更影响分析困难；
- 模型维护依赖人工搜索；
- 资产之间容易出现不一致。

**P1 应对方向**

- 建立统一 Metadata Asset 模型；
- 支持数据库、文档、API 和代码仓库连接；
- 将本体元素与来源资产关联；
- 保存来源位置、版本和采集时间。

### 3.4 问题四：本体建设高度依赖专家人工投入

**典型场景**

本体工程人员需要阅读大量业务文档、数据库定义和代码，手工识别：

- 业务实体；
- 属性；
- 关系；
- 术语；
- 约束；
- 同义词和冲突定义。

当数据源规模扩大时，人工梳理成本显著增加。

**根本原因**

- 现有资产缺少统一语义抽取机制；
- 本体发现工具与企业 IT 资产缺少集成；
- 本体专家知识难以复用；
- 不同来源的候选模型缺少统一合并机制。

**业务影响**

- 本体建设周期较长；
- 领域专家投入较多；
- 项目重复建设；
- 维护成本随业务变化增加。

**P1 应对方向**

- 利用 AI 辅助提取候选概念和关系；
- 建立统一发现任务模型；
- 将 AI 结果转化为可审核候选；
- 保留证据、置信信息和人工修改记录。

### 3.5 问题五：AI 生成的语义模型缺少可信管理机制

**典型场景**

LLM 根据业务文档生成一组实体和关系，但可能存在：

- 将不同概念合并；
- 忽略业务上下文；
- 推断不存在的关系；
- 误解字段定义；
- 生成不符合标准的结构；
- 不同运行结果存在差异。

**根本原因**

- 模型输出存在不确定性；
- 缺少来源证据；
- 缺少统一审核流程；
- 缺少独立验证机制；
- 缺少模型和提示词版本记录。

**业务影响**

- 生成结果难以直接用于生产；
- 错误语义可能传递给下游应用；
- 审核人员无法判断模型依据；
- 结果难以复现和追溯。

**P1 应对方向**

- AI 输出默认作为候选；
- 每项重要建议关联来源证据；
- 建立审核状态和人工决策记录；
- 通过独立验证器检查结构与语义；
- 记录发现任务、Provider 和模型版本。

### 3.6 问题六：本体缺少持续维护和版本管理

**典型场景**

企业业务发生变化：

- 客户类型增加；
- 订单状态调整；
- 业务对象拆分；
- 数据库字段迁移；
- API 接口升级。

如果本体只以文件形式保存，团队可能难以确认：

- 哪个版本是正式版本；
- 哪些内容发生了变化；
- 哪些应用仍依赖旧版本；
- 变更是否破坏兼容性；
- 是否能够恢复历史版本。

**根本原因**

- 本体与软件工程资产管理流程脱节；
- 版本管理不完善；
- 缺少语义差异比较；
- 缺少发布和审核记录。

**业务影响**

- 模型变更风险增加；
- 下游应用可能使用过期定义；
- 历史语义难以追溯；
- 本体维护依赖人工沟通。

**P1 应对方向**

- 建立本体版本和快照机制；
- 保存变更记录；
- 提供版本差异比较；
- 发布时关联验证结果和审核记录；
- 为后续影响分析保留依赖关系。

### 3.7 问题七：语义资产难以被不同 AI 应用复用

**典型场景**

企业同时建设销售 Agent、客服 Agent、数据分析 Agent 和运营 Agent。

如果各应用分别维护自己的业务定义，就可能出现：

- 客户定义不同；
- 订单状态解释不同；
- 指标口径不同；
- 实体关联规则不同。

**根本原因**

- 缺少统一语义资产目录；
- 本体缺少标准接口；
- 模型发布和分发机制不完善；
- 应用与语义版本缺少关联。

**业务影响**

- 重复开发；
- 语义不一致；
- 应用间协作困难；
- AI 系统维护成本增加。

**P1 应对方向**

- 建立统一本体资产管理；
- 提供本体查询和导出接口；
- 使用稳定版本标识；
- 支持不同应用引用已发布的语义资产。

## 4. 问题之间的关系

以上问题并非彼此独立。

它们构成一个相互影响的链条：

```text
企业 IT 资产分散
       │
       ▼
业务语义定义不一致
       │
       ▼
跨系统语义关联缺失
       │
       ▼
本体建设依赖人工
       │
       ▼
AI 生成结果缺少审核和证据
       │
       ▼
语义质量难以保证
       │
       ▼
版本和变更难以管理
       │
       ▼
语义资产难以持续复用
```

因此，解决方案不能只提供一个本体编辑器，也不能只提供一个 LLM 自动生成接口。

需要将数据连接、语义发现、建模、审核、验证和版本管理组织成统一的工程流程。

## 6. 产品不解决的问题

为避免产品范围无限扩张，以下问题不属于 P1 首期直接解决范围：

### 6.1 数据存储与事务问题

P1 不负责替代企业数据库，也不承担核心业务数据的事务处理。

### 6.2 完整数据治理问题

P1 不替代完整的数据目录、主数据管理、数据质量和数据安全治理系统。

### 6.3 Agent 运行和调度问题

P1 提供语义资产，但不负责 Agent Runtime、Agent 调度、运行监控和多 Agent 协作管理。

### 6.4 生产业务操作授权问题

P1 不承担生产环境业务操作审批、权限决策和执行治理。

### 6.5 通用工作流问题

P1 只实现本体生命周期所需的审核和发布流程，不建设通用企业流程引擎。

## 7. 问题验证与需求调研

本文件中的问题定义属于产品假设和需求分析基线，需要通过真实场景进一步验证。

建议采用以下方法：

| 验证方法 | 目标 | 产出 |
|---|---|---|
| 领域专家访谈 | 确认术语和本体维护痛点 | 访谈记录 |
| 数据架构师访谈 | 确认跨系统语义问题 | 数据模型案例 |
| 现有系统调研 | 识别数据源和资产类型 | IT 资产清单 |
| 典型业务案例 | 验证完整本体工程链路 | 场景说明 |
| 技术 POC | 验证 AI 发现和标准互操作 | POC 测试记录 |
| MVP 测试 | 验证核心问题是否得到改善 | 验收报告 |

### 7.1 建议的首个验证案例

采用模拟 CRM、OMS 和 ERP 数据源，构建企业客户与订单领域本体。

验证内容：

1. 能否采集不同系统的数据库元信息；
2. 能否识别潜在客户、购买方和财务账户概念；
3. 能否发现相似字段和潜在映射关系；
4. 能否为候选关系提供来源证据；
5. 能否通过人工审核修正错误映射；
6. 能否保存和验证正式本体；
7. 能否发布并通过接口查询。

### 7.2 验证原则

- 使用固定、可复现的测试数据；
- 区分 AI 候选和人工确认结果；
- 记录发现任务配置和版本；
- 不以单次演示代替测试；
- 不虚构准确率、效率提升或成本下降指标；
- 对未验证的问题明确标注。

## 8. 需求优先级建议

| 优先级 | 能力 | 理由 |
|---|---|---|
| P0 | 项目与本体资产管理 | 所有功能的基础 |
| P0 | 统一元模型 | 决定平台数据结构 |
| P0 | 本体创建、编辑和导入导出 | 形成基本建模能力 |
| P0 | 结构与引用验证 | 保证基本模型质量 |
| P0 | 版本管理 | 保证资产可追溯 |
| P1 | 数据源连接和元数据采集 | 为自动发现提供输入 |
| P1 | AI 本体发现 | 降低人工建模成本 |
| P1 | 候选审核和证据追溯 | 保证 AI 结果可控 |
| P1 | 本体发布接口 | 支持下游复用 |
| P2 | 高级语义推理 | 按真实场景逐步增加 |
| P2 | 大规模实例图谱管理 | 需根据数据规模另行决策 |
| P2 | 复杂协同和企业审批 | 属于后续扩展方向 |

优先级是当前规划建议，最终应以 MVP 评审和技术验证结果为准。
