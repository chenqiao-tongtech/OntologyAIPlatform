## 1. 文档目的

本文件建立 P1 产品需求从业务问题到工程实现和测试验收的完整追踪关系。

核心追踪链路：

**业务问题 → 用户场景 → 产品需求 → 产品能力 → 系统模块 → API → 数据对象 → 测试用例 → 验收结果**

通过这套追踪关系，确保：

1. 每项产品需求都有明确来源。
2. 每项需求都有对应的产品能力和责任模块。
3. 需要通过 API 实现的需求有明确接口规划。
4. 核心需求能够映射到数据对象。
5. 每项可验收需求都有测试用例。
6. 需求发生变化时，可以识别受影响的模块、接口和测试。

本文档是需求追踪的主索引。具体的功能验收条件见 `acceptance-criteria.md`。

## 3. 产品问题追踪

依据产品立项文档，P1 首先解决以下七类问题。

| 问题编号 | 问题描述 | 主要影响 | 对应产品方向 |
|---|---|---|---|
| P-01 | 同一业务概念在不同系统中定义不一致 | 语义冲突、数据解释困难 | 统一本体模型 |
| P-02 | 同一术语在不同业务上下文中含义不同 | 概念歧义 | 领域与上下文管理 |
| P-03 | 企业语义信息分散在数据库、文档、API 和代码中 | 语义资产难以发现 | 数据连接与元数据采集 |
| P-04 | 本体发现依赖专家手工分析 | 建模成本高 | AI 辅助发现 |
| P-05 | AI 生成的本体缺乏可信审核机制 | 模型质量和来源难以确认 | 证据、审核和质量验证 |
| P-06 | 本体缺乏持续维护和版本管理 | 语义变化不可追踪 | 版本、变更与发布 |
| P-07 | 本体难以被其他 AI 应用和系统复用 | 语义资产价值难以发挥 | 标准导出和 API |

## 10. MVP 追踪基线

MVP 的 P0 需求：

- FR-001、FR-002；
- FR-003、FR-004、FR-005、FR-007；
- FR-018、FR-019；
- FR-020、FR-021、FR-022；
- FR-023、FR-024；
- FR-028、FR-029、FR-030。

MVP 端到端验收至少应覆盖：

1. 创建项目；
2. 创建本体；
3. 编辑类、属性和关系；
4. 执行结构和基础语义验证；
5. 修复错误并重新验证；
6. 创建版本快照；
7. 比较两个版本；
8. 导出标准格式；
9. 重新解析导出文件；
10. 验证权限和审计。

## 11. 需求变更管理

新增或修改需求时，必须更新：

1. 需求编号和描述；
2. 来源问题或用户用例；
3. 优先级；
4. 对应产品能力；
5. 责任模块；
6. 受影响 API；
7. 受影响数据对象；
8. 测试用例；
9. 验收标准；
10. 变更记录。

任何 P0 需求的删除或降级都应经过产品和技术评审。

## 12. 完成状态定义

建议使用以下状态：

| 状态 | 定义 |
|---|---|
| Proposed | 已提出，未评审 |
| Approved | 已进入需求基线 |
| Designed | 已完成设计 |
| In Development | 正在开发 |
| Implemented | 代码已实现 |
| Tested | 自动化或人工测试完成 |
| Accepted | 验收通过 |
| Deferred | 延后 |
| Deprecated | 已废弃 |

不得将 Designed 或 Implemented 误标为 Accepted。
