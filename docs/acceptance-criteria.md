# P1 功能需求与验收标准

**文档路径：** `docs/product/acceptance-criteria.md`  
**产品：** P1 Ontology Engineering Platform  
**版本：** V1.0  
**日期：** 2026-11-21  
**状态：** 设计基线，待评审

## 1. 文档目的

本文档将 P1 产品功能转化为可验证的验收条件，建立需求与测试之间的对应关系。

验收标准用于：

- 产品需求评审；
- 开发任务拆分；
- API 设计；
- 测试用例编写；
- 版本发布判断；
- 需求变更影响分析。

## 2. 验收原则

### 2.1 每项需求必须可验证

避免使用以下无法直接验收的表述：

- 系统应当足够智能；
- 本体编辑体验良好；
- 系统应支持灵活扩展；
- 系统性能应当优秀。

应转化为可观察的行为和结果。

例如：

“系统支持本体版本管理”应拆解为：

- 用户能够创建版本快照；
- 快照具有唯一标识；
- 快照内容不受后续编辑影响；
- 用户能够查询历史版本；
- 用户能够比较两个版本；
- 系统能够记录版本创建人和创建时间。

### 2.2 验收必须覆盖异常情况

不能只验证正常流程，还需要验证：

- 非法输入；
- 重复对象；
- 无效引用；
- 权限不足；
- 文件解析失败；
- 后台任务失败；
- 数据库事务失败；
- 导出失败。

### 2.3 验收结果必须留有记录

每次验收至少保存：

- 需求编号；
- 测试用例编号；
- 测试环境；
- 测试数据版本；
- 执行时间；
- 执行结果；
- 缺陷记录；
- 测试证据。

## 3. 功能验收标准

### 3.1 项目管理

#### FR-001 创建项目

**需求描述：** 用户能够创建本体工程项目。

验收条件：

1. 用户提交项目名称和必要信息后，系统创建项目。
2. 系统生成稳定且唯一的项目 ID。
3. 项目具有创建时间和创建人信息。
4. 创建成功后能够通过项目 ID 查询。
5. 项目名称、描述等字段符合约定的校验规则。
6. 无项目创建权限的用户不能创建项目。

测试用例：

- TC-001-01：合法信息创建项目；
- TC-001-02：缺少必填字段；
- TC-001-03：重复或冲突的项目标识；
- TC-001-04：无权限创建项目。

#### FR-002 查询和更新项目

验收条件：

1. 用户能够查询有权访问的项目。
2. 用户能够查询项目详情。
3. 授权用户能够修改项目基本信息。
4. 无权用户不能修改项目。
5. 归档项目的状态能够被正确展示。

测试用例：

- TC-002-01：查询项目列表；
- TC-002-02：查询项目详情；
- TC-002-03：更新项目；
- TC-002-04：无权限更新；
- TC-002-05：查询归档项目。

### 3.2 本体对象管理

#### FR-003 创建和编辑本体

验收条件：

1. 用户能够在指定项目下创建本体。
2. 本体具有唯一 ID。
3. 本体必须归属于一个有效项目。
4. 用户能够修改本体名称、描述和其他允许修改的元数据。
5. 用户能够查询本体详情。
6. 不存在的项目不能作为本体归属对象。

测试用例：

- TC-003-01：创建本体；
- TC-003-02：修改本体元数据；
- TC-003-03：查询本体；
- TC-003-04：使用无效项目 ID 创建本体。

#### FR-004 类管理

验收条件：

1. 用户能够创建本体类。
2. 类具有唯一标识。
3. 类可以配置名称、描述和继承关系。
4. 继承关系引用必须有效。
5. 删除被其他对象引用的类时，系统必须阻止非法删除或要求明确处理引用。

测试用例：

- TC-004-01：创建类；
- TC-004-02：重复类 ID；
- TC-004-03：创建有效继承关系；
- TC-004-04：无效父类引用；
- TC-004-05：删除被引用的类。

#### FR-005 属性与关系管理

验收条件：

1. 用户能够创建数据属性和对象关系。
2. 属性具有明确类型。
3. 关系能够关联定义域和值域。
4. 定义域和值域引用必须有效。
5. 不支持的属性类型必须被拒绝。
6. 关系引用不能指向不存在的本体对象。

测试用例：

- TC-005-01：创建数据属性；
- TC-005-02：创建对象关系；
- TC-005-03：非法属性类型；
- TC-005-04：无效定义域；
- TC-005-05：无效值域。

### 3.3 本体导入导出

#### FR-006 本体导入

验收条件：

1. 系统能够识别约定支持的文件格式。
2. 成功解析的内容能够转换为平台内部模型。
3. 解析错误应包含文件或对象定位信息（在技术上可提供时）。
4. 导入失败时不得产生不完整的正式模型。
5. 导入操作需要记录来源文件摘要、格式、操作者和时间。
6. 不支持的格式应明确提示。

测试用例：

- TC-006-01：导入有效 Turtle；
- TC-006-02：导入有效 RDF/XML；
- TC-006-03：导入支持范围内的 JSON-LD；
- TC-006-04：非法 RDF 文件；
- TC-006-05：不支持的格式；
- TC-006-06：重复导入；
- TC-006-07：导入中断后的数据一致性。

#### FR-007 本体导出

验收条件：

1. 用户能够导出指定本体或版本。
2. 导出格式必须在支持列表中。
3. 导出内容能够被对应解析器重新读取。
4. 导出结果必须对应明确的本体版本或当前模型状态。
5. 导出失败应返回明确错误。
6. 导出操作应保留审计记录。

测试用例：

- TC-007-01：导出 Turtle；
- TC-007-02：导出 RDF/XML；
- TC-007-03：导出 JSON；
- TC-007-04：导出不存在的版本；
- TC-007-05：导出后重新解析；
- TC-007-06：无权限导出。

### 3.4 质量验证

#### FR-008 结构验证

验收条件：

1. 能检查对象 ID 唯一性。
2. 能检查必填字段。
3. 能检查类、属性和关系引用完整性。
4. 能检查基本对象类型合法性。
5. 验证结果能够区分错误和警告。
6. 每次验证生成独立验证记录。
7. 验证结果能够查询和追踪。

测试用例：

- TC-008-01：正常本体验证；
- TC-008-02：重复 ID；
- TC-008-03：缺少必填字段；
- TC-008-04：无效引用；
- TC-008-05：非法对象类型；
- TC-008-06：验证结果查询。

#### FR-009 基础语义验证

验收条件：

1. 能够执行约定的基础语义规则。
2. 能够验证属性定义域和值域。
3. 能够检查约束引用。
4. 对无法自动判断的语义问题，应输出警告或人工检查建议。
5. 验证结果必须关联本体版本或明确的模型快照。

测试用例：

- TC-009-01：合法语义约束；
- TC-009-02：定义域不匹配；
- TC-009-03：值域不匹配；
- TC-009-04：约束定义错误；
- TC-009-05：人工检查建议生成。

#### FR-010 验证结果管理

验收条件：

1. 验证记录包含验证时间、对象、规则集和执行状态。
2. 每条 Finding 包含问题类型、严重级别和对象定位。
3. 用户能够查询历史验证记录。
4. 修复模型后可以重新执行验证。
5. 新旧验证结果相互独立，不覆盖历史记录。

测试用例：

- TC-010-01：生成验证记录；
- TC-010-02：查询历史验证；
- TC-010-03：修复后重新验证；
- TC-010-04：比较两次验证结果。

### 3.5 版本与变更管理

#### FR-011 创建版本

验收条件：

1. 用户能够为本体创建版本快照。
2. 版本具有唯一标识和版本号。
3. 版本记录创建人、创建时间和变更说明。
4. 快照保存本体在创建时的确定内容。
5. 后续模型编辑不影响历史快照。
6. 不满足发布前置条件的版本不能被标记为正式发布版本。

测试用例：

- TC-011-01：创建版本；
- TC-011-02：重复版本号；
- TC-011-03：快照内容稳定性；
- TC-011-04：版本元数据查询；
- TC-011-05：非法发布状态转换。

#### FR-012 版本比较

验收条件：

1. 用户能够选择两个有效版本进行比较。
2. 系统能够识别新增对象。
3. 系统能够识别删除对象。
4. 系统能够识别修改对象。
5. 比较结果能够定位到具体对象。
6. 版本比较不得修改原始版本。

测试用例：

- TC-012-01：比较无差异版本；
- TC-012-02：比较新增对象；
- TC-012-03：比较删除对象；
- TC-012-04：比较修改对象；
- TC-012-05：无效版本比较。

### 3.6 权限和审计

#### FR-013 项目级权限

验收条件：

1. 用户只能访问授权项目。
2. 写操作必须进行权限校验。
3. 只读用户不能执行修改操作。
4. 权限不足时返回明确错误。
5. 后端 API 必须执行权限检查，不能仅依赖前端隐藏按钮。

测试用例：

- TC-013-01：授权访问；
- TC-013-02：未授权访问；
- TC-013-03：只读用户修改；
- TC-013-04：跨项目资源访问；
- TC-013-05：直接调用受保护 API。

#### FR-014 操作审计

验收条件：

1. 关键写操作生成审计事件。
2. 审计事件包含操作者、时间、操作类型和目标对象。
3. 失败操作在适用情况下也应记录。
4. 普通业务用户不能随意修改审计记录。
5. 审计信息能够按项目、对象和时间查询。

测试用例：

- TC-014-01：创建操作审计；
- TC-014-02：更新操作审计；
- TC-014-03：删除操作审计；
- TC-014-04：失败操作审计；
- TC-014-05：审计权限控制。

## 4. 非功能验收标准

| 编号 | 非功能要求 | 验收条件 |
|---|---|---|
| NFR-001 | 可扩展性 | 新增连接器和验证规则不要求修改所有核心模块 |
| NFR-002 | 可维护性 | 提供数据库迁移、配置说明和结构化日志 |
| NFR-003 | 私有化部署 | 能按照文档在目标环境完成部署 |
| NFR-004 | 安全 | 凭证不以明文存入普通业务记录 |
| NFR-005 | 标准兼容 | 支持格式通过对应解析器检查 |
| NFR-006 | 可观测性 | 后台任务有状态、错误和执行记录 |
| NFR-007 | 可测试性 | 核心业务模块具有自动化测试 |
| NFR-008 | 数据完整性 | 关键对象满足唯一性、引用和事务一致性要求 |
| NFR-009 | 备份恢复 | 能按部署说明备份并恢复核心数据 |
| NFR-010 | 隔离性 | 不同项目之间不能通过未授权 API 访问彼此数据 |

性能验收指标应在确定部署规格、数据规模和并发目标后单独定义，不能在缺乏测试依据时预设为已达成。

## 5. 端到端验收场景

### 场景：客户与订单本体工程

**准备数据：**

- Customer 类；
- Order 类；
- Product 类；
- OrderItem 类；
- 客户、订单、商品之间的关系；
- 一份包含错误引用的测试本体文件。

**执行步骤：**

1. 创建“客户与订单”项目。
2. 创建 Customer、Order、Product、OrderItem 等类。
3. 创建属性和关系。
4. 执行结构验证。
5. 修复故意引入的无效引用。
6. 执行语义验证。
7. 创建 V1.0 快照。
8. 修改一个属性并新增一个关系。
9. 创建 V1.1 快照。
10. 比较 V1.0 和 V1.1。
11. 导出 V1.1。
12. 重新解析导出文件。
13. 查询项目和本体的操作审计记录。

**预期结果：**

- 项目和本体能够正常创建；
- 验证能够发现预设问题；
- 修复后验证结果符合预期；
- V1.0 和 V1.1 内容独立；
- 版本比较能识别新增和修改；
- 导出文件能够重新解析；
- 关键操作均可追踪。

## 7. 缺陷等级建议

| 等级 | 定义 | 处理原则 |
|---|---|---|
| Blocker | 核心流程无法执行或数据严重损坏 | 阻断验收 |
| Critical | 安全、权限或核心数据一致性问题 | 阻断发布 |
| Major | 核心功能不符合验收要求 | 原则上修复后验收 |
| Minor | 非关键体验或边界问题 | 评估后纳入后续版本 |
| Improvement | 功能优化建议 | 纳入产品待办 |

## 8. 验收结论

一个功能只有在以下条件均满足时，才可以标记为验收通过：

- 实现符合需求；
- 正常路径测试通过；
- 重要异常路径测试通过；
- 权限检查通过；
- 相关数据和审计记录正确；
- 自动化测试通过；
- 使用和部署文档更新。

功能开发完成、代码合并或页面可访问，都不能单独作为验收通过的依据。
